## 1. 本教程解决什么

以 MiniRPC 源码为唯一教材，按"依赖与可验证性"排序，带你建立三层能力：

1. **读**：任意模块能指出"这个类/函数解决协议栈里的哪个问题"；
2. **改**：能独立修改协议、网络层、RPC 语义并跑通测试；
3. **讲**：能不看资料讲清一次 RPC 调用从 `SerializeToString` 到 `resp.result()` 的字节流生命周期。

## 3. 学习路径总览（顺序不可调整）

| 章 | 主题 | 时长 | 核心验证手段 |
|---|---:|---:|---|
| 01 | 协议与编解码 | 2.5h | codec_test |
| 02 | 网络层 | 5h | echo_server / buffer_test / gdb |
| 03 | 线程池 | 2h | threadpool_test |
| 04 | RPC 核心 | 4h | rpc_test / calculator demo |
| 05 | 服务治理 | 2.5h | loadbalancer_test / registry_test / 故障剔除演示 |
| 06 | 工程化 | 2h | 全量 ctest / benchmark 复跑 |

排序依据：

- 协议是**契约**，被 codec_test 精确锁定，独立且最小——先学它，后面所有层都围绕"这条字节流"展开；
- 网络层是**难点**（事件分发 + 生命周期），必须在协议之后学，才能理解"为什么需要长度字段"；
- 线程池是**并发工具**，服务端线程边界（loop 拆包 / 池执行 / runInLoop 回包）贯穿第 4 章；
- RPC 层是**组装**：把 codec + net + thread 拼成服务端/客户端；
- 治理层是**分布式扩展**：注册、心跳、负载均衡；
- 工程化是**数据验证**：测试覆盖 + 压测结论。

## 4. 学习方法（每章都这么做）

### 4.1 字节流主线

整个教程以一条 RPC 消息的字节流生命周期为纵轴。每学一层，回答同一组问题：

```text
此刻字节在哪？           （用户对象 / protobuf 缓冲 / Buffer / socket 内核缓冲）
谁在哪个线程操作？        （loop 线程 / 线程池线程 / 调用方线程）
持有哪把锁？             （taskQueueMutex_ / pendingFunctors mutex_ / ioMutex_）
哪个对象持有这个 Buffer？ （TcpConnection::inputBuffer_ / RpcChannel::inputBuffer_）
```

### 4.2 规格驱动

`tests/*.cpp` 是本项目的可执行规格。每章先读对应测试的断言，再读实现——断言即"应当成立的性质"。

### 4.3 破坏性实验

每章至少做一次"改坏 → 观察失败模式 → 恢复"：改 kMaxBodySize、去掉重试分支、停心跳、改虚拟节点数。失败模式比正常路径更能暴露设计意图。

### 4.4 gdb / 日志验证线程归属

`EventLoop::assertInLoopThread` 在错误线程调用会 `abort()`（[src/net/EventLoop.cpp:assertInLoopThread]）。用 gdb 在 `handleRead` 断点查看调用栈，确认"拆包在 loop 线程"这一事实。

## 5. 环境准备（一次性）

```bash
cd /home/nina/minRPC
cmake -B build && cmake --build build -j        # 构建
ctest --test-dir build --output-on-failure      # 全量测试
```

说明：

- 构建依赖 protobuf（protoc 3.21.12），CMake 默认开启 `MINIRPC_ENABLE_PROTOBUF`；
- `rpc_test`、`registry_test` 需要 TCP socket，若在受限沙箱中需放行网络或单独运行；
- 压测结论基于 Release 构建（`cmake -B build-rel -DCMAKE_BUILD_TYPE=Release`）。
