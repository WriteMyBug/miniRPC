## 4. 技术原理

### 4.1 注册-心跳-发现-剔除时序

```text
节点A/B                注册中心                   客户端(LB)
  │ Register(service, node) │                      │
  │────────────────────────>│                      │
  │ Heartbeat(每 interval)  │                      │
  │────────────────────────>│                      │
  │                         │  Discover(service)   │
  │                         │<─────────────────────│
  │                         │── 存活节点列表 ───────>│ 缓存 + TTL
  │                         │                      │ 选节点 → 调用
  │ (B 宕机，心跳停止)        │                      │
  │                         │ purgeExpired:        │
  │                         │ now-last > timeout → 删除 B
  │                         │  Discover (TTL 刷新)  │
  │                         │── 只剩 A ────────────>│
```

### 4.2 心跳参数：timeout ≥ 3×interval

- interval：心跳发送周期；timeout：判定死亡的最长沉默期；
- 若 timeout 接近 interval，单次网络抖动即误杀；
- 本项目默认 timeout=6000ms、示例 interval=500~2000ms（满足 ≥3×），测试中用 1200/300ms。

### 4.3 轮询 vs 一致性哈希

```text
轮询：next = atomic_index++ % node_count —— 实现简单、绝对均匀；同一 key 请求落在不同节点。
一致性哈希：
  节点 key 哈希为环上点（每节点 100 个虚拟点 "node#0..99"）
  请求 key 哈希 → lower_bound 环上第一个 >= 的点 → 该节点
  性质：同一 key 稳定同一节点；增删节点只影响相邻弧段（最小迁移）
```

虚拟节点必要性：节点少时直接哈希分布倾斜（实测某节点可能完全无请求），虚拟点摊平弧段。

### 4.4 TTL 刷新与故障转移

```text
needRefresh：节点列表空 或 now-lastRefresh >= refreshIntervalMs → refreshNodes
调用失败分类：
  kClosed / kSystem / kTimeout → 连接级：refreshNodes 后换节点重试一次
  业务错误（如除零）→ 不重试
```

## 5. 重点实现拆解

### 5.1 RegistryServiceImpl 状态与语义 [src/registry/RegistryServiceImpl.cpp]

```text
数据结构：services_[serviceName][nodeKey] = NodeEntry{node, lastHeartbeat}
nodeKey = host:port

Register    → 写入/覆盖 entry，lastHeartbeat=now
Heartbeat   → 已存在则刷新时间戳；未注册则报错（必须先 Register）
Discover    → purgeExpired 后返回存活节点（排序保证确定性）
Unregister  → 删除（优雅下线）
purgeExpired→ now - lastHeartbeat > timeout → 删除并日志
evictionLoop→ 每 500ms 加锁 purge（与请求处理互不阻塞）
```

### 5.2 RpcServiceNode [src/rpc/RpcServiceNode.cpp]

```text
start()        → server.start() + registerSelf（同步）+ 启动心跳线程
heartbeatLoop  → 每 interval 发 Heartbeat；cv wait 可被 stop 立即打断
stopHeartbeat  → 置 stop、唤醒、join；【不注销】= 模拟崩溃
shutdown()     → stopHeartbeat + unregisterSelf = 优雅下线
```

故障剔除验收依赖 `stopHeartbeat`：进程/服务仍在，但注册中心收不到心跳，超时后自动剔除。

### 5.3 LoadBalanceChannel [src/rpc/LoadBalanceChannel.cpp]

```text
refreshNodes：Discover → nodes_ 更新 → roundRobin_.setNodeCount / consistentHash_.setNodes
selectNodeKey：
  一致性哈希 → hashKey = request 序列化字节，环选节点（同请求同节点）
  轮询       → nodes_[roundRobin_.next() % n]
channelFor  ：nodeKey("host:port") 首次创建 RpcChannel 并缓存，复用连接
CallMethod：
  needRefresh → refreshNodes
  nodes_ 空 → kNoService
  调 channelFor(nodeKey)->CallMethod
  失败且 code ∈ {kClosed,kSystem,kTimeout} 且 n>1：
    failedNodeKey_ = nodeKey; refreshNodes(); 换节点重试一次
  done != nullptr 时不自动重试（避免回调多次触发）
```

### 5.4 ConsistentHash 实现 [src/rpc/LoadBalancer.cpp]

```text
hash64：std::hash<string>（libstdc++ _Hash_bytes，雪崩性优于 FNV-1a——
  FNV 对 "node#0"~"node#99" 短串的虚拟点会聚集，实测分布失效）
setNodes：清空环，每节点插入 100 个 "key#i" 虚拟点
selectNode：lower_bound(hash(key))，越过末尾则回绕到 begin
```

## 6. 验证实验

### 实验 1：故障剔除演示

```bash
./build/registry/registry_server 18800 &
./build/examples/rpc_node 9001 node-a 18800 500 &
./build/examples/rpc_node 9002 node-b 18800 500 &
sleep 1.5
./build/examples/lb_client 18800 20 rr      # 预期 node-a:10 node-b:10
kill %3                                       # 杀掉 node-b
sleep 6                                       # 等心跳超时
./build/examples/lb_client 18800 10 rr      # 预期 nodes=1，仅 node-a
```

注册中心日志预期出现：`Registry: evict stale node ...@127.0.0.1:9002`。

### 实验 2：自动化验收

```bash
./build/tests/loadbalancer_test
./build/tests/registry_test
```

loadbalancer_test 验证：轮询序列、同 key 稳定、200 key 覆盖全部节点、移除节点后非受影响 key 不变。
registry_test 验证：双节点轮询分布、一致性哈希粘性、node-b 停心跳后 Discover 只剩 1 节点且 LB 调用全成功。

### 实验 3：破坏性——虚拟节点数

把 [include/minirpc/rpc/LoadBalancer.h] 的默认虚拟节点数 100 改为 5，重编译跑 loadbalancer_test，分布断言应失败；恢复 100 后通过。验证虚拟节点对均匀性的作用。

### 实验 4：破坏性——心跳超时

`registry_server` 第 2 个参数（heartbeat_timeout_ms）改为 1000，重复实验 1，观察剔除提前；体会"超时越小剔除越快、越易误杀"。

## 7. 面试追问

1. 心跳 timeout 与 interval 的关系？设太大会怎样、太小会怎样？
2. 崩溃与优雅下线的剔除路径有何不同？（答：崩溃=心跳超时被动剔除；优雅=Unregister 主动删除）
3. 客户端节点列表怎么知道过期？（答：TTL，needRefresh 用 lastRefresh_ 判断）
4. 一致性哈希下节点挂了，哪些请求受影响？（答：仅原本落在该节点弧段的请求迁移到后继节点）
5. 为什么客户端每节点复用一条连接？（答：建连成本高（TCP 握手），复用减少延迟与 fd 消耗）
