## 4. 技术原理

### 4.1 为什么需要自定义协议

TCP 只保证"字节流按序到达"，不保证"一次 recv 恰好是一条消息"。要在字节流上恢复消息边界，标准做法是 TLV（Type-Length-Value）或固定头 + 长度字段。本项目采用后者：固定 24 字节头，其中 `bodyLen` 声明 body 长度。

### 4.2 分层：传输帧 vs 业务信封

```text
一条 TCP 报文 = ProtocolHeader(24B) + body
                              └─ body 是 protobuf 序列化的 RpcRequest / RpcResponse

RpcRequest  { string method; bytes request; }    // 方法全名 + 序列化请求
RpcResponse { int32 error_code; string error_message; bytes response; }
```

分离动机：

- 协议头只关心"传输帧"：长度、序号、类型，与业务无关；
- 信封关心"RPC 语义"：方法分发、错误码、响应体；
- 结果：Codec 保持通用，业务协议（信封）可独立演进，网络层无需感知。

### 4.3 24 字节头部布局

```text
偏移  长度  字段      类型     语义
0     4    magic     uint32  0x4D494E52（"MINR"），首包校验，防脏数据
4     1    version   uint8   = 1，版本协商
5     1    type      uint8   1=请求 2=响应
6     2    flags     uint16  预留标志位
8     8    seq       uint64  序列号：请求-响应匹配、重试去重
16    4    bodyLen   uint32  body 字节数
20    4    reserved  uint32  预留
```

`static_assert(sizeof(ProtocolHeader) == 24)` 在编译期锁定布局（[include/minirpc/codec/Protocol.h]）。

### 4.4 字节序

多字节字段（magic/flags/seq/bodyLen/reserved）在网络上统一使用大端（网络字节序）：

- 编码：htonl/htons/htobe64；
- 解码：ntohl/ntohs/be64toh。

若不统一，跨机器（小端 x86 vs 大端机器）解析出的 seq/bodyLen 会错乱，表现为"请求匹配不上响应"或"长度异常被防御逻辑拒绝"。

## 5. 重点实现拆解

### 5.1 编码 [src/codec/Codec.cpp:encode]

```cpp
void Codec::encode(const ProtocolMessage& msg, Buffer* out) {
  appendU32(out, msg.header.magic);
  out->append(reinterpret_cast<const char*>(&msg.header.version), 1);
  out->append(reinterpret_cast<const char*>(&msg.header.type), 1);
  appendU16(out, msg.header.flags);
  appendU64(out, msg.header.seq);
  appendU32(out, static_cast<uint32_t>(msg.body.size()));
  appendU32(out, msg.header.reserved);
  out->append(msg.body);
}
```

要点：

- 写入顺序 = 布局顺序，逐字节可对照；
- version/type 单字节，不涉及字节序；
- bodyLen 取 `msg.body.size()`，而不是信任调用方填的 header.bodyLen——编码端以真实数据为准。

### 5.2 解码 [src/codec/Codec.cpp:tryDecode]

```cpp
if (in->readableBytes() < kHeaderSize) return std::nullopt;   // 头未齐
const char* p = in->peek();                                   // 只看不取
if (readU32(p) != kMagic) throw ...;                          // 脏数据
// 解析 version/type/flags/seq/bodyLen/reserved
if (h.version != kProtocolVersion) throw ...;
if (h.bodyLen > kMaxBodySize) throw ...;
if (in->readableBytes() < kHeaderSize + h.bodyLen) return std::nullopt;  // body 未齐
in->retrieve(kHeaderSize);                                    // 齐了才消费
msg.body = in->retrieveAsString(h.bodyLen);
```

三段式语义：

| 情况 | 返回 | Buffer 游标 |
|---|---|---|
| 头未齐（<24B） | nullopt | 不动 |
| 头齐、body 未齐（<24+bodyLen） | nullopt | 不动 |
| 完整报文 | ProtocolMessage | 前移 24+bodyLen |

这就是"半包不消费、粘包循环消费"：上层 `while (tryDecode)` 一次取出所有完整报文，剩余半包留在 Buffer 等待下一次 readFd。

### 5.3 防御 [src/codec/Codec.cpp:tryDecode]

- 魔数校验：对端连错端口或脏数据，直接抛 `runtime_error`，服务端在 [src/rpc/RpcServer.cpp:onMessage] 捕获后 `conn->shutdown()`；
- 版本校验：不兼容版本显式报错而非静默解析；
- `kMaxBodySize = 64MB`：恶意声明超大 bodyLen 会导致 `retrieveAsString` 分配巨大内存，上限校验先于分配。

## 7. 面试追问

1. 为什么长度字段放在头部而不是先收齐再猜？（答：O(1) 判断是否完整，避免缓存整条流）
2. tryDecode 在 body 未齐时返回 nullopt，Buffer 游标动了没有？（答：没有，peek 不消费）
3. 粘包时 `while(tryDecode)` 循环会死循环吗？（答：不会；每次消费 24+bodyLen，且只有数据够才消费）
4. 字节序写错会有什么现象？（答：seq/bodyLen 错乱 → 响应匹配失败或触发长度防御）
5. 信封为什么包在 body 里而不是放在协议头？（答：协议头固定 24B 保持传输层通用，方法名/错误码属 RPC 语义，用 protobuf 承载可扩展）
