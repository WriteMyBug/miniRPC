## 4. 技术原理

### 4.1 测试策略：断言即规格

本项目无测试框架，用自研 `expect(cond, expr, line)` + 宏 `EXPECT`，失败打印 `FAIL line N` 并累计计数，退出码非 0。测试文件同时是"规格文档"：断言描述性质，实现必须满足。

测试分两层：

- 单元：buffer/threadpool/codec/loadbalancer（无网络依赖，可离线跑）；
- 集成：rpc/registry（真实 socket + 多线程 + 心跳时序，需要网络权限）。

### 4.2 压测指标定义

```text
QPS = 总请求数 / 总耗时(秒)
avg = Σ延迟 / N
p50/p90/p99 = 延迟排序后 50%/90%/99% 位置的值
max = 最大值
```

延迟以微秒计：每次调用前后 `steady_clock::now()` 差值（[benchmark/benchmark.cpp]）。P99 反映长尾；max 受调度抖动影响大，不作为主要指标。

### 4.3 压测方法

- 并发梯度：1/10/20/30/40/50/60/80/100/200 客户端线程，每线程独立 RpcChannel；
- 每档总请求约 2 万（并发大时整除折算）；
- 服务端资源：压测期间每 100ms 采样 `/proc/<pid>/stat`（utime/stime）与 `/proc/<pid>/status`（VmRSS），CPU% = Δ(utime+stime)/HZ / Δt × 100（单核百分比）；
- Release 构建（`build-rel`）为报告基准；Debug 约慢 30-40%。

| loadbalancer_test | 选路性质 | 轮询循环；同 key 同节点；200 key 覆盖 3 节点；删节点后非受影响 key 不变 |

### 5.2 压测统计 [benchmark/benchmark.cpp]

```cpp
auto pct = [&all](double p) {
  return all[std::min<size_t>(all.size()-1, static_cast<size_t>(all.size()*p))];
};
const long qps = elapsedSec > 0 ? static_cast<long>(all.size()/elapsedSec) : 0;
```

注意 `all.size()*p` 向下取整索引：p=0.99 时取排序后第 99% 个样本。CSV 追加写便于一次跑多档汇总。

### 5.3 压测报告的三个结论（必须能解释）

| 结论 | 数据 | 技术解释 |
|---|---|---|
| 单 Reactor 40 并发峰值约 3.16 万 QPS | 30:30038 / 40:31587 / 50:28933 | 并发充分掩盖单次调用延迟（约 1.1ms p50）；更高并发进入排队 |
| 单 Reactor 下 4 线程池最优 | 4 线程优于 8/16 | 全局 priority_queue 互斥 + notify_all 惊群随线程数放大；且回包仍受单 reactor 限制 |
| 单 Reactor 瓶颈已被多 Reactor 验证并解决 | 单：200 并发 2.25 万 QPS、CPU 1.26 核；多（io=8/pool=16）：约 8 万 QPS、CPU 4.18 核 | 多 Reactor 把读/写/唤醒分摊到多核（EventLoopPool + 连接分发）；剩余排队来自客户端侧调度 |

优化已落地：多 Reactor（每核一个 EventLoop）见 [../decisions.md](../decisions.md) D8 与 [../benchmark/report.md](../benchmark/report.md) 第 6 节。后续方向：批量唤醒与合并发送、异步客户端（在途并发 + seq 匹配）、多进程 + SO_REUSEPORT。

## 6. 验证实验

### 实验 1：全量测试

```bash
ctest --test-dir build --output-on-failure
```

预期 6/6 通过（rpc_test/registry_test 需网络权限）。

### 实验 2：复跑压测梯度

```bash
cmake -B build-rel -DCMAKE_BUILD_TYPE=Release && cmake --build build-rel -j
./build-rel/examples/calculator_server 8888 standalone 4 &
for C in 1 10 40 100 200; do
  ./build-rel/benchmark/benchmark 127.0.0.1 8888 $C $((20000/C))
done
```

预期：单客户端 p50 约 250us；40 并发 QPS 接近 3 万、P99 < 5ms；200 并发 QPS 回落至 2.7 万左右且 P99 升高（排队）。

### 实验 3：观察服务端资源

压测同时循环采样服务端 `/proc/<pid>/stat` 与 `status`（可参照报告方法），复现"CPU 约 1.3 核、RSS 约 6.6MB"。

### 实验 4：破坏性——线程池大小

`calculator_server 8888 standalone 8` 与 `... 16` 各跑一次 200 并发，对比 QPS 与 4 线程配置，验证"线程数不是越多越好"。

## 7. 面试追问

1. QPS 与 P99 分别衡量什么？为什么压测要同时看？（答：吞吐与延迟分布/长尾，单看其一会被误导）
2. 为什么 40 并发吞吐最高？（答：延迟约 1.1ms、单连接串行，约 40 并发才能把单 reactor 带宽填满；再多进入排队）
3. 为什么 8/16 线程反而更慢？（答：队列锁竞争 + notify_all 惊群；且回包路径不随业务线程数扩展）
4. 为什么服务端 CPU 只有 1.3 核就说"瓶颈在单 reactor"？（答：CPU 未饱和但吞吐封顶，说明瓶颈是串行处理路径——eventfd 唤醒 + pending 任务投递）
5. 压测报告的可复现性怎么保证？（答：固定环境（WSL2/16 核/内核版本）、Release 构建、固定并发梯度与请求量、记录方法）
