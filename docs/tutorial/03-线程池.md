## 4. 技术原理

### 4.1 生产者-消费者模型

```text
生产者（任意线程）                   消费者（N 个工作线程）
submit(fn) ──入队──> taskQueue_  <──取堆顶── WorkerThread
                        priority_queue
                        + taskQueueMutex_
                        + notEmpty_（有任务） / notFull_（有空位）

future 路径：packaged_task 的 future 返回给调用方，异常经 future 传播
回调路径：结果 push 到 callbackQueue_，主线程调 runPendingCallbacks() 取
```

### 4.2 两种模式

- `PoolMode::kFixed`：固定线程数，工作线程永久阻塞等待（`notEmpty_.wait`）；
- `PoolMode::kCached`：任务堆积且有空闲线程配额时动态创建线程，超额线程 60s 无任务退出。

本项目服务端固定使用 kFixed。

### 4.3 服务端线程边界（本项目的核心约束）

```text
loop 线程：readv 收数据 → Codec::tryDecode 拆包 → 提交线程池
线程池线程：解析信封 → 反射调用 Service 方法 → conn->send
loop 线程：runInLoop 真正写 socket
```

拆包不能在池线程做：`TcpConnection::inputBuffer_` 属于 loop 线程（无锁访问）；业务与 IO 分离是单 Reactor 模型的正确用法。

## 5. 重点实现拆解

### 5.1 submit 模板 [include/minirpc/thread/ThreadPool.h:submit]

```text
调用方传 f 与 args
  → 打包 packaged_task<ReturnType()>（参数进 std::tuple）
  → 队列元素 {priority, 调用 packaged_task 的 lambda}
  → 返回 taskPtr->get_future()
```

关键点：

- packaged_task 用 `shared_ptr` 持有，lambda 与 future 都安全；
- 执行时 `std::apply(std::move(f), std::move(tup))` 展开参数；
- 任务抛异常由 WorkerThread 的 try/catch 捕获，异常经 future 传给 `get()`，工作线程不死。

### 5.2 enqueueTask [src/thread/ThreadPool.cpp:enqueueTask]

```cpp
notFull_.wait_for(lock, timeout, [this] {
  return taskQueueSize_ < maxTaskQueueSize_ || !isRunning_;
});
```

- 队列满最多等 60s（可配），超时返回 false；`submit` 抛 `runtime_error`，`trySubmitFor` 返回 `nullopt`；
- push 后 `notEmpty_.notify_all()` 唤醒工作线程；
- kCached 模式在"队列长度 > 空闲线程数且未达上限"时动态扩线程。

### 5.3 WorkerThread [src/thread/ThreadPool.cpp:WorkerThread]

```text
for(;;):
  if (!isRunning_) break
  lock
  while 队列空: waitForWork（谓词含 !isRunning_，保证关闭时能退出）
  idleThreadCount_--
  取堆顶任务，pop，unlock
  try { taskFn(); } catch(...) { Log }   // 异常隔离
  idleThreadCount_++
```

### 5.4 关闭语义 [src/thread/ThreadPool.cpp:~ThreadPool]

```cpp
isRunning_ = false;
notEmpty_.notify_all();
notFull_.notify_all();
exitCond_.wait(lock, [this] { return threads_.empty(); });
runPendingCallbacks();   // 兜底执行残留回调
```

顺序很重要：先置标志再唤醒；等待谓词"线程集合为空"保证析构时无工作线程仍访问成员。

### 5.5 CreateThread 竞态修复 [src/thread/ThreadPool.cpp:CreateThread]

原实现先 detach 再注册 thread id：线程若提前退出，`threadExit` 可能先于注册执行，留下脏 id，析构 `exitCond_` 等待永远不满足。修复：**先在 `threadSetMutex_` 下注册 id，再 detach**（见 [docs/decisions.md](../decisions.md) D1）。

## 6. 验证实验

### 实验 1：跑线程池测试

```bash
./build/tests/threadpool_test
```

对照 [tests/threadpool_test.cpp] 五个用例：基本 submit、500 并发任务、异常传播、回调模式、单线程优先级顺序（HIGH→NORMAL→LOW）。

### 实验 2：线程数对比

写一个临时程序：分别用 1 线程与 8 线程提交 1000 个 `i*i` 任务（任务带 1ms 延时模拟耗时），统计总耗时并解释差异（并行收益 vs 队列锁竞争）。

### 实验 3：破坏性——移除异常隔离

把 [src/thread/ThreadPool.cpp:WorkerThread] 的 try/catch 临时去掉，提交一个抛异常任务，观察工作线程随异常退出、线程池线程数下降；恢复后重跑确认异常被隔离。

## 7. 面试追问

1. submit 返回的 future 与队列里的任务是什么关系？（答：同一 packaged_task 的两个视图；任务执行结果/异常经它传递）
2. 队列满时为什么是"等待"而不是"拒绝"？（答：背压策略可配置：等待超时抛异常 / trySubmitFor 返回 nullopt）
3. 析构时任务还在跑/排队会怎样？（答：置停止标志，正在执行的任务跑完；排队任务不再执行；等线程集合清空才返回）
4. 为什么服务端回包要 runInLoop 而不是池线程直接 write？（答：fd 与输出缓冲属 loop 线程，多线程并发写同一 socket 需加锁；投递回 loop 天然串行）
5. 为什么 4 线程比 8/16 快？（答：全局队列互斥 + notify_all 惊群随线程数放大，且回包吞吐受单 reactor 限制；实测见第 6 章）
