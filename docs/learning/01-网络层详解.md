## 3. 架构设计详解（新手友好）

### 3.1 一句话

**一个线程（EventLoop）用 epoll 同时盯着所有连接，哪个 fd 可读/可写就回调谁；网络 IO 之外的重活（业务处理）交给线程池，避免阻塞事件循环。**

### 3.2 组件关系图

```text
                           EventLoop（主线程，一个进程一个）
          ┌───────────────────┼───────────────────────┐
          │                   │                       │
     EpollPoller          wakeupChannel            pendingFunctors
     （epoll fd +        （eventfd，跨线程         （其他线程投递的任务）
      fd→Channel 映射）    唤醒用）
          │
   epoll_wait 返回就绪的 Channel 列表
          │
   ┌──────┴───────┬──────────────┐
 Channel        Channel        Channel
 （监听 fd）     （连接1）       （连接2）
    │              │              │
 TcpServer    TcpConnection   TcpConnection
 （accept +     （输入Buffer +    （输入Buffer +
  连接管理 map）  输出Buffer）      输出Buffer）
```

### 3.3 三个关键抽象

1. **Channel（fd 的"遥控器"）**：不拥有 fd，只把"fd + 感兴趣的事件 + 回调"绑在一起。fd 可读时执行 readCallback，可写时执行 writeCallback。
2. **EpollPoller（epoll 的封装）**：负责 `epoll_ctl` 增删改和 `epoll_wait` 拿就绪事件；把内核事件转成 Channel 列表。
3. **EventLoop（心脏）**：一个线程一个，循环执行"等事件 → 分发 → 跑任务"。

### 3.4 一次读事件的旅程（务必能复述）

```text
客户端发来数据
  → epoll_wait 返回 [connChannel(EPOLLIN)]
  → connChannel->handleEvent()
  → 命中 readCallback_ = TcpConnection::handleRead
  → inputBuffer_.readFd(fd)（readv 一次尽量读完）
  → 数据进入 Buffer，调用用户回调（如 echo：取出、原样发回）
```

## 4. 重点实现拆解

### 4.1 EventLoop::loop 主循环（src/net/EventLoop.cpp）

```cpp
while (!quit_) {
  poller_->poll(10000, &activeChannels);   // 等最多 10 秒
  for (Channel* ch : activeChannels)
    ch->handleEvent();                     // 分发就绪事件
  doPendingFunctors();                     // 执行其他线程投递的任务
}
```

要点：
- poll 超时 10 秒是为了让"没有网络事件时"也能定期执行 pending 任务；
- 分发和任务执行都在 loop 线程，所以**除了任务队列的锁，网络层几乎没有锁**。

### 4.2 Channel 事件映射（src/net/Channel.cpp）

```text
EPOLLHUP 且没有 EPOLLIN  → closeCallback（对端关闭）
EPOLLERR                → errorCallback
EPOLLIN/EPOLLPRI/RDHUP  → readCallback
EPOLLOUT                → writeCallback
```

为什么 HUP 单独处理？epoll 会在对端关闭时同时给 HUP，若忽略会导致连接不回收。

### 4.3 Buffer 的粘包半包（src/net/Buffer.cpp）

Buffer 内部是 `vector<char>` + 两个游标：

```text
┌──────────┬──────────────┬──────────────┬──────────┐
│ prepend  │ 已读(可回收)  │  未读数据    │  可写空间  │
│  8 字节   │ readerIndex_  │  reader→writer │ writer→end │
└──────────┴──────────────┴──────────────┴──────────┘
```

- `readableBytes()`：还能读多少（= 数据长度）；
- `retrieve(n)`：消费 n 字节（只移游标，不删除数据，省拷贝）；
- 空间不够时 `ensureWritableBytes` 把未读数据搬到头部再扩容；
- `readFd` 用 `readv`：先写进剩余空间，再写进 64KB 栈上 extrabuf，一次读尽量多，减少系统调用。

**粘包/半包怎么破？** 不是 Buffer 单独解决的，而是"Buffer 攒数据 + 协议头长度字段"配合（阶段 3 讲）。Buffer 只保证：来的字节都存住、按需消费、不丢不重。

### 4.4 TcpConnection 生命周期（src/net/TcpConnection.cpp）

```text
accept 到新 fd
  → TcpServer 创建 shared_ptr<TcpConnection>，放进 connections_ map
  → connectEstablished：channel 注册读事件
  → 数据来了 → handleRead → messageCallback（用户业务）
  → 对端关闭 → handleRead 读到 0 → handleClose
      → channel disableAll（从 epoll 摘除）
      → closeCallback → TcpServer 从 map 里 erase
      → shared_ptr 引用归零 → 析构 → 关闭 fd
```

为什么用 `shared_ptr`？因为回调可能在其他线程（线程池）还拿着连接对象（比如要回包），不能"关闭就立刻释放内存"，必须等所有引用都离开。

### 4.5 eventfd 唤醒（src/net/EventLoop.cpp）

别的线程要往 loop 投递任务（比如线程池要回包）：

```cpp
queueInLoop(functor) {
  加锁 push 到 pendingFunctors_;
  写一个字节到 wakeupFd_;   // eventfd，唤醒阻塞中的 epoll_wait
}
```

loop 线程醒来后先消费 wakeupFd（handleWakeup），再执行 pending 任务。这就是"跨线程安全地让主线程干活"的机制。

## 5. 新手最常卡住的三个点

1. **"为什么读不到数据"**：多半忘了处理 EAGAIN，或 fd 不是非阻塞。
2. **"连接关了我还写"**：对端关闭后 write 会触发 SIGPIPE（默认杀进程）。TcpServer::start 里 `signal(SIGPIPE, SIG_IGN)` 就是为了这个。
3. **"为什么我的回调在别的线程执行"**：EventLoop 有 `assertInLoopThread`，跨线程调用会直接 abort——这是设计上的安全检查。
