## 3. 架构设计详解

### 3.1 一句话

**服务节点启动时向注册中心报个到（注册），之后每隔几秒报个平安（心跳）；注册中心发现谁好久没报平安就把谁删掉（剔除）；客户端定期问注册中心"现在谁活着"（发现），再按策略挑一个节点去调用（负载均衡）。**

### 3.2 时序图

```text
节点A/B                注册中心                客户端(LB通道)
  │ Register(service,node) │                      │
  │───────────────────────>│                      │
  │ Heartbeat(每N ms)      │                      │
  │───────────────────────>│                      │
  │                        │  Discover(service)   │
  │                        │<─────────────────────│
  │                        │── 存活节点列表 ───────>│
  │                        │                      │ 选节点 → 调用
  │ (节点B宕机，心跳停止)   │                      │
  │                        │ 超时后 purgeExpired   │
  │                        │ 删除B                 │
  │                        │  Discover (TTL刷新)   │
  │                        │<─────────────────────│
  │                        │── 只剩节点A ─────────>│
```

## 4. 重点实现拆解

### 4.1 RegistryServiceImpl（src/registry/RegistryServiceImpl.cpp）

数据结构是两层 map：

```cpp
unordered_map<服务名, unordered_map<节点key, NodeEntry>>
// 节点key = "host:port"
// NodeEntry = { NodeInfo node, time_point lastHeartbeat }
```

四个方法：

| 方法 | 行为 |
|---|---|
| Register | 写入/刷新 entry，lastHeartbeat = now |
| Heartbeat | 节点已存在 → 刷新 lastHeartbeat；不存在 → 报错 |
| Discover | 先 purge 过期节点，返回存活列表（按 host:port 排序，保证确定性） |
| Unregister | 直接删除（优雅下线） |

剔除是**后台线程**干的（每 500ms 扫一次）：

```cpp
if (now - lastHeartbeat > heartbeatTimeout_)   // 默认 6s
  删除该节点，打日志 "evict stale node"
```

时间参数建议：`timeout >= 3 × interval`（本项目示例 500ms 心跳 / 1.5s 超时），避免网络抖动误杀。

### 4.2 RpcServiceNode（src/rpc/RpcServiceNode.cpp）

```text
start()       → server.start() + 同步 Register + 启动心跳线程
heartbeatLoop → 每 interval 发一次 Heartbeat（条件变量等待可立即唤醒）
stopHeartbeat → 置停止标志、唤醒、join；【不注销】——模拟"崩溃"
shutdown()    → stopHeartbeat + Unregister——模拟"优雅下线"
```

故障剔除验收就是靠 `stopHeartbeat`：进程还在、服务还在，但注册中心收不到心跳，超时后自动剔除。面试说清"心跳缺失 = 认为宕机"即可。

### 4.3 LoadBalanceChannel（src/rpc/LoadBalanceChannel.cpp）

客户端侧三件事：

1. **节点列表 TTL 刷新**：`needRefresh()`（列表空 或 超过 refreshIntervalMs）→ `refreshNodes()` 调 Discover；
2. **选节点**：轮询用原子计数器取模；一致性哈希把请求序列化字节当 key 上环选节点；
3. **每节点一个 RpcChannel**：`channelFor(nodeKey)` 首次创建、之后复用（连接是珍贵资源）。

故障转移（面试重点）：

```text
调用失败 → 看 controller 错误码
  是 kClosed/kSystem/kTimeout（连接级）？
    → refreshNodes()（可能节点已被剔除）
    → 换一个节点重试一次（一致性哈希模式下故意避开失败节点）
  是业务错误（如除零）？→ 不重试，直接返回
```

为什么业务错误不重试？重试只会把同一个错误再拿一遍，还白白增加服务端压力。

### 4.4 轮询 vs 一致性哈希（LoadBalancer）

```text
轮询：index_++ % n —— 实现简单、绝对均匀；但"同一个 key 的请求"会打到不同节点。
一致性哈希：把节点哈希成环上的点，请求 key 哈希后顺时针找第一个节点
  —— 同一 key 稳定同一节点（粘性），加/删节点只影响一小段（最小迁移）。
```

虚拟节点为什么必要？节点少时直接哈希容易倾斜（某节点弧段特别大）；每个节点放 100 个虚拟点（`node#0..99`）后分布均匀。实现里用 `std::hash<string>` 而不是 FNV-1a，因为 FNV-1a 对 "a#0"~"a#99" 这类短串雪崩差（虚拟点全挤在一起）——这是踩过坑的结论，测试 `loadbalancer_test` 里有分布断言。
