## 3. 架构设计详解

### 3.1 一句话

**一堆工作线程 + 一个带锁的任务队列：生产者把任务放进队列，空闲线程取一个执行；提交时立即返回"取结果的凭证（future）"。**

### 3.2 组件图

```text
                     ThreadPool
   ┌────────────────────┼─────────────────────┐
   │                    │                     │
 taskQueue_          workers(线程)          callbackQueue_
 (priority_queue)    (detach 的工作线程)     (回调模式专用)
   │  锁: taskQueueMutex_
   │  条件变量: notEmpty_(有活干) / notFull_(队列有空位)
   │
   └── 线程集合 threads_(unordered_set<thread::id>)：用于析构时确认全部退出
```

### 3.3 两种"拿结果"的方式

1. **future 模式**（`submit`）：调用方阻塞 `future.get()` 等结果；
2. **回调模式**（`submitWithCallback`）：任务在工作线程执行，结果入"回调队列"，主线程自己调 `runPendingCallbacks()` 取回调——适合"结果回到事件循环线程"的场景（本项目 RpcServer 没用到，但面试可讲）。

## 4. 重点实现拆解

### 4.1 submit：任意函数 → future（ThreadPool.h 模板）

```text
用户传函数 f 和参数 args
  → 打包成 packaged_task<ReturnType()>（参数先放进 std::tuple）
  → 入队：priority_queue 里放 {priority, 一个调用 packaged_task 的 lambda}
  → 返回 taskPtr->get_future()
```

关键点：
- `std::apply(std::move(f), std::move(tup))` 把元组里的参数展开调用；
- packaged_task 被 `shared_ptr` 持有，保证队列里的 lambda 和 future 都安全；
- 任务执行抛异常不会杀死工作线程：WorkerThread 里 try/catch 包住，异常通过 future 传给调用方。

### 4.2 入队：队列满怎么办（enqueueTask）

```cpp
notFull_.wait_for(lock, 60s, [this] {
  return taskQueueSize_ < maxTaskQueueSize_ || !isRunning_;
});
```

队列满会等最多 60 秒（可配）；`trySubmitFor` 变体超时返回 `nullopt` 而不是抛异常。

### 4.3 工作线程循环（WorkerThread）

```text
for(;;):
  if (!isRunning_) break;                // 停止信号
  lock 队列
  while 队列空:
    等待 notEmpty（FIXED 模式永久等；CACHED 额外线程等 60s 超时退出）
  idleThreadCount_--
  取走堆顶任务
  unlock
  try 执行任务 catch 记录日志
  idleThreadCount_++
```

### 4.4 关闭：为什么不会死锁（~ThreadPool）

```cpp
isRunning_ = false;
notEmpty_.notify_all();      // 唤醒所有等待中的工作线程
notFull_.notify_all();
exitCond_.wait(lock, [this] { return threads_.empty(); });  // 等全部线程退出
```

要点：先置停止标志再唤醒；工作线程的等待谓词是"有任务**或**停止"，所以能退出；析构等 `threads_` 清空才继续，避免悬空。

### 4.5 我们修过的一个坑（面试加分点）

原实现 CreateThread **先 detach 再往 threads_ 注册 id**：若线程立刻退出，可能"退出时还没注册"，析构等 `threads_` 为空会死等。修复：**先注册 id 再 detach**。能讲出这个改动，说明你真的读过。

### 4.6 为什么 4 线程最优（压测结论）

任务队列是全局互斥 + notify_all：线程越多，取任务时的锁竞争和"惊群"越明显；而且业务线程干完活还要把结果送回单 Reactor，业务线程再多，回包还是主线程一个在发。实测：4 线程 ≈ 2.05 万 QPS（Debug）/ 3.16 万（Release），8/16 线程反而更慢。**"先压测再优化"是最好的回答。**
