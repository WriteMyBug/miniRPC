# MiniRPC 面试追问 QA（场景制）

> 与 [interview-qa.md](interview-qa.md)（按模块）不同，本文按"面试场景"组织，每个问题附
> **答案要点** 和 **面试官可能继续追问的下一层**。建议先自己答，再看要点。

## 1. 开场与定位

### Q1. 介绍一下你的项目？

答案要点：先说一句话定位（学习型 C++17 RPC 框架，约 5000 行），再按"网络层 → 协议 → RPC → 治理 → 压测"讲四层，控制在 2 分钟。

追问：为什么做这个，不用 gRPC？

要点：一是查漏补缺，把网络/并发/序列化/分布式串成一条线；二是规模可控，每个模块能讲清；gRPC 太复杂，反而讲不清底层。计划书里明确列了非目标（一致性协议、跨语言、全功能注册中心）。

### Q2. 这是你自己写的吗？

要点：直接承认"部分用了 AI 辅助"，然后立刻证明理解：每个模块都独立调试/修改过，压测是自己跑的，能现场改代码。重点在"我能讲清 + 我能改"，不在"是不是一行行敲的"。

追问：哪些是你自己写的？

要点：可以具体化：协议头设计、重试语义、Buffer 半包处理、心跳剔除这些是自己推的；线程池复用了之前的练习项目并修了一个竞态（先注册线程 id 再 detach）。

## 2. 架构与全链路

### Q3. 一次 RPC 调用完整走一遍？

要点：客户端 Stub → RpcChannel 组装信封（方法全名 + 序列化请求）→ 24B 头（type=request, seq）→ TCP → 服务端 epoll 可读 → Buffer 收 → Codec 拆包 → 线程池 → 查注册表 → 反射创建对象 → CallMethod → 结果装 RpcResponse（同 seq）回发 → 客户端 poll 收包 → 按 seq 匹配 → 填 response。

追问：哪一步在哪个线程？

要点：拆包在 loop 线程；业务在池线程；回包经 conn->send → runInLoop 投回 loop 线程；客户端同步调用在调用方线程（通道内部 ioMutex_ 串行）。

追问：为什么拆包不能放线程池？

要点：inputBuffer_ 属于 loop 线程且无锁访问，跨线程共享需要加锁；拆包很轻（memcpy 级别的活），不值得跨线程。

## 3. 网络层深挖

### Q4. epoll 为什么能管理大量连接？LT 和 ET 区别？

要点：epoll 由内核维护就绪链表，事件驱动，避免每连接一个线程的栈/上下文开销。LT 有数据就通知（每次 epoll_wait 都会返回，直到读完）；ET 只在状态变化通知一次，需要读到 EAGAIN。本项目用 LT：简单可靠不丢事件。

追问：ET 有什么坑？

要点：读不干净会饿死后续事件；要 while 循环读直到 EAGAIN；还要小心一次读太多导致其他 fd 饥饿（可限次）。

追问：惊群是什么？你遇到吗？

要点：多个线程同时 epoll_wait 同一个 fd，事件到来全部被唤醒但只有一个能处理。本项目单 Reactor 不存在该问题；多 Reactor 方案可用 EPOLLEXCLUSIVE 或 SO_REUSEPORT 缓解。

### Q5. Buffer 怎么处理粘包半包？

要点：TCP 是字节流，无消息边界。方案 = Buffer 攒字节 + 协议头带长度。tryDecode 先 peek 校验长度，数据不够返回 nullopt 且不消费；够了才 retrieve。粘包时 while 循环一次取多条。

追问：retrieve 为什么不删数据？

要点：只移 readerIndex_，O(1)；空间不足时 ensureWritableBytes 才把未读数据搬到头部并扩容，减少频繁拷贝。

追问：readv 是干嘛的？

要点：一次系统调用写两个缓冲（Buffer 剩余空间 + 64KB 栈上兜底），尽量读尽，减少 read 次数。

## 4. 线程池深挖

### Q6. 线程池怎么实现？怎么拿返回值？

要点：priority_queue（按优先级）+ 条件变量；submit 用 packaged_task 打包，返回 future，异常经 future 传播。队列满时 wait_for 60s，超时抛异常（trySubmitFor 返回 nullopt）。

追问：为什么 4 线程比 8/16 快？

要点：这是**单 Reactor 下**的实测结论——回包仍要回单个事件循环，业务线程再多也提高不了回包吞吐，而全局队列互斥 + notify_all 惊群随线程数放大。升级多 Reactor 后 IO 与业务解耦，pool=16 又能继续提升（200 并发 2.25 万 → 8 万 QPS），所以结论要区分场景，不能背死。

追问：怎么优雅关闭？

要点：置 isRunning_=false → notify_all → 工作线程在谓词（有任务或停止）下退出 → exitCond_ 等 threads_ 集合清空再析构，避免悬空访问。

追问：你修过什么 bug？

要点：CreateThread 原实现先 detach 再注册线程 id，线程提前退出会留下脏 id，析构可能死等；改成先注册 id 再 detach。

## 5. 协议与重试深挖

### Q7. 协议头每个字段为什么存在？

要点：魔数防脏数据；长度解决粘包半包；seq 用于请求-响应匹配和重试去重；版本做兼容；类型区分请求/响应；多字节字段统一大端。

追问：字节序写错会怎样？

要点：seq/bodyLen 解析错乱 → 响应匹配失败或触发长度防御，属于"能定位但难排查"的问题；所以用 htonl/htons/htobe64 显式转换。

### Q8. 超时重试怎么保证不串包？

要点：每次重试换新 seq；旧响应即使迟到，seq 对不上直接被丢弃；每次尝试前 Reset controller，避免上次超时的失败标记残留。

追问：重试会不会重复执行？幂等怎么办？

要点：会。超时后服务端可能已执行，重试是"可重放"假设；seq 去重只防串包，不防重复执行。面试要主动承认这个限制，并说业务侧需要幂等或去重（这是真实系统要考虑的）。

追问：什么情况不重试？

要点：只有 kTimeout 重试；连接关闭（kClosed）、系统错误（kSystem）、服务端明确业务错误（如除零）都不重试。

## 6. 服务治理深挖

### Q9. 注册中心为什么自己写，不用 etcd？

要点：项目定位是讲清原理，且计划书把全功能注册中心列为非目标；用自己框架的 RpcServer 承载 RegistryService，正好验证框架通用性——注册中心本身只是一个普通 RPC 服务。

追问：心跳超时怎么定？

要点：默认 6s、示例 500ms 心跳；规则 timeout ≥ 3×interval，避免网络抖动误杀；测试里用 300ms/1200ms 加速验证。

追问：崩溃和优雅下线的区别？

要点：优雅下线调 Unregister 主动删除；崩溃没有 Unregister，靠心跳超时被动剔除。

### Q10. 一致性哈希为什么用虚拟节点？

要点：节点少时直接哈希分布倾斜（实测某节点可能完全接不到请求）；每节点 100 个虚拟点摊平弧段。移除节点时只有落在该节点弧段的 key 迁移，其余不变（最小迁移，有测试断言）。

追问：哈希函数为什么用 std::hash 不用 FNV？

要点：实测 FNV-1a 对 "node#0"~"node#99" 这类短串雪崩差，虚拟点全挤在一起；std::hash（libstdc++ _Hash_bytes）分布均匀。

追问：客户端怎么知道节点挂了？

要点：节点列表 TTL 缓存（默认 3s），调用时检查是否过期再刷新；调用失败若是连接级错误（kClosed/kSystem/kTimeout），先刷新列表再换节点重试一次；业务错误不重试。

## 7. 压测数字深挖

### Q11. 压测数字怎么测的？

要点：Release 构建、WSL2 固定环境；N 个客户端线程各自独立 RpcChannel，逐次记录延迟（steady_clock），QPS = 总请求/总耗时，P99 是排序后 99% 分位；并发梯度 1~200；每档约 2 万请求。方法在 benchmark/report.md。

追问：单 Reactor 为什么 40 并发最高？多 Reactor 后呢？

要点：单请求延迟约 1.1ms，单 Reactor 串行处理；40 并发刚好填满主循环带宽，再高进入排队。多 Reactor 把读/写/唤醒分摊到多核，200 并发 QPS 从 2.25 万升到约 8 万、P99 从 61ms 降到 6.5ms。

追问：单 Reactor 时 CPU 才 1.3 核，凭什么说瓶颈在事件循环？

要点：CPU 未饱和但吞吐封顶，说明瓶颈不是计算，而是串行处理路径——每次响应都要 eventfd 唤醒 + pending 任务投递。这个推理链（数据 → 排除法 → 定位）比结论本身更重要；而且升级多 Reactor 后吞吐确实提升约 3.5 倍，验证了定位正确。

追问：怎么优化？

要点：多 Reactor 已落地（EventLoopPool + 连接轮询分发，CPU 1.26 → 4.18 核）；剩余方向：批量唤醒/合并发送、异步客户端（在途并发 + seq 匹配）、多进程 + SO_REUSEPORT。要说明"知道为什么能优化、代价是什么（线程间负载均衡/复杂度）"。

## 8. 工程与人设

### Q12. 测试怎么写的？

要点：没引测试框架，自研 expect 断言 + 宏；6 个目标分单元（buffer/threadpool/codec/loadbalancer）和集成（rpc/registry，真实 socket + 心跳时序）。测试即规格：断言描述性质。

追问：集成测试怎么保证不 flaky？

要点：固定端口、服务端就绪后再发请求（promise 通知）、心跳/剔除用短参数（300ms/1200ms）加速、等注册中心剔除后再断言。

### Q13. 为什么只做同步客户端？

要点：第 3 周目标是打通链路，同步 + 串行实现最可靠；异步客户端（在途并发、回调）是计划里的可选加分项，留作后续。主动说"知道异步要解决什么：seq 匹配 + 回调线程安全"。

### Q14. 项目里你觉得最难/最后悔的点？

要点（选真实经历讲）：线程池"先 detach 后注册 id"的竞态（析构死等）；或压测发现"线程越多越慢"打破直觉；或粘包半包一开始没设计好。讲"踩坑 → 定位方法（日志/压测/gdb）→ 修复"比讲"我很强"有用。

## 9. 现场改代码常见考题

1. **加一个 RPC 方法**（如 Pow）：改 proto → 重编译自动生成 → 实现 Service 方法 → 客户端调用。考核"反射分发下框架零改动"是否真懂。
2. **改协议**（如给 flags 加压缩位）：encode/tryDecode 同步改，注意字节序与 static_assert。
3. **改参数**（超时/重试/线程数/心跳）：要能说出改完的预期效果（耗时、误杀率、QPS 变化）。
4. **修 bug 场景**：连接关闭后线程池还回包 → 指出 send 用 weak_ptr + runInLoop 防悬空；或问"队列满了怎么办"→ 背压语义。
